# P1.0.4 — ручная Chrome Runtime Acceptance

Дата подготовки: 2026-11-15
Статус: **OPTIONAL / НЕ ТРЕБУЕТСЯ ДЛЯ ФИНАЛИЗАЦИИ**

Основной Chrome flow подтверждён пользователем и зафиксирован в `P104_RESULTS.md`. В соответствии с ускоренным итерационным процессом этот расширенный checklist сохраняется только для диагностики при обнаружении дефекта; выполнять его целиком перед следующими этапами не требуется.

Используйте только синтетические тексты. Не отправляйте реальные запросы моделям в рамках приёмки: официальные сайты достаточно открыть, а тестовые ответы вставить вручную из подготовленного локального текста.

## 1. Резервная копия и сборка

1. Полностью закройте Chrome-профиль, используемый для Multi-LLM.
2. В PowerShell из `C:\Multi-LLM` создайте согласованную SQLite-копию:

```powershell
.\.venv\Scripts\python.exe .\scripts\backup_research_db.py
```

Скрипт читает исходную БД в режиме `mode=ro`, проверяет `integrity_check`, создаёт копию в `%LOCALAPPDATA%\Multi-LLM\Backups` и печатает точный путь. Сохраните этот путь в результатах.

3. Убедитесь, что production build существует:

```powershell
Set-Location C:\Multi-LLM\extension
npm run build
```

4. Запустите изолированный Chrome-профиль, откройте `chrome://extensions`, включите режим разработчика и нажмите **Reload** у ранее загруженного unpacked-расширения из `C:\Multi-LLM\extension\dist`. Фактический ожидаемый ID: `bjjaimmalalgcdhofmggchjafgijdlkn`.
5. Проверьте регистрацию и временный stdio probe:

```powershell
Set-Location C:\Multi-LLM
.\scripts\check_native_host.ps1 -ExtensionId bjjaimmalalgcdhofmggchjafgijdlkn
```

Ожидается `Registration checks: PASS` и JSON с `operations_checked: 22`, `confirmed_responses: 4`, `final_phase: COMPARISON`.

## 2. Основной сценарий

1. Откройте Side Panel и Workspace. Проверьте `Python подключён` в обоих интерфейсах.
2. Откройте существующую `P103 Runtime Test`. После первого подключения миграция v2 должна пройти автоматически; сессия и четыре прежних задания должны сохраниться.
3. Создайте новую сессию `P104 Manual Bridge Test` с синтетическим вопросом и начните исследование. Должны появиться четыре назначения: Gemini, DeepSeek, Qwen, Grok.
4. Для каждого задания нажмите **Задание**. Проверьте реальный текст, версию и SHA-256. Нажмите **Копировать** и вручную вставьте содержимое в локальный текстовый редактор: текст должен совпадать полностью.
5. Нажмите **Открыть сайт** для каждого провайдера. Должен открыться только официальный HTTPS-адрес без prompt/query/hash. Ничего не отправляйте сайту.
6. Для каждого задания нажмите **Импорт ответа** и вставьте разные синтетические ответы, включая Unicode, CRLF и длинный текст. До клика **Подтвердить и сохранить** статус и SQLite не должны измениться.
7. На втором шаге проверьте provider, `web_manual`, модель `не указана`, UTF-8 byte count, начало и конец. Нажмите **Подтвердить и сохранить** один раз. После ACK должны появиться `Получено`, версия 1, размер, hash и дата.
8. Откройте сохранённый ответ через **Просмотреть** и сравните начало/конец с исходным текстом.
9. Для одного ответа выберите **Новая редакция**, сохраните изменённый текст и проверьте версию 2. Исходная версия не должна заменяться в SQLite (это дополнительно покрыто автоматическим тестом).
10. После четырёх `RECEIVED` нажмите **Следующий этап**. Сервер должен перевести сессию в `COMPARISON`; интерфейс показывает placeholder P1.0.5 и не создаёт фиктивный результат сравнения.

## 3. Негативные и recovery-сценарии

1. В новой тестовой сессии попробуйте импортировать пустую строку и строку из пробелов — переход к preview/save должен быть заблокирован.
2. Введите неподтверждённый текст и закройте диалог — должно появиться предупреждение, текст не должен сохраниться.
3. На задаче без ответа выберите **Недоступно / замена**, сохраните содержательную причину, затем:
   - проверьте, что пропуск без причины невозможен;
   - переведите её в `SKIPPED_WITH_REASON` и подтвердите, что gate проходит только при трёх `RECEIVED` и отдельной общей причине перехода;
   - либо переназначьте на свободного провайдера из каталога и проверьте prompt version 2/status `PROMPT_READY`.
4. Попытка выбрать уже назначенного провайдера должна быть отклонена. Задача с подтверждённым ответом не должна переназначаться.
5. Во время заполненного, но ещё не подтверждённого import-диалога выполните штатный unregister:

```powershell
.\scripts\unregister_native_host.ps1 -ExtensionId bjjaimmalalgcdhofmggchjafgijdlkn
```

Нажмите подтверждение: текст должен остаться в форме, а UI — показать offline-ошибку. Затем восстановите регистрацию:

```powershell
.\scripts\register_native_host.ps1 -ExtensionId bjjaimmalalgcdhofmggchjafgijdlkn
```

Нажмите reconnect/retry с тем же содержимым. Должен появиться ровно один логический результат без дубликата.
6. Одновременно откройте Side Panel и Workspace. После mutation проверьте одинаковые status/hash/version/session revision в обоих окнах.
7. Поставьте сессию на паузу: импорт/изменение ответа должны быть отклонены. Возобновите её и проверьте повторную синхронизацию.
8. Полностью перезапустите изолированный Chrome. Активная сессия и подтверждённые ответы должны восстановиться; незавершённый volatile draft восстанавливаться не должен.
9. В DevTools → Application проверьте `chrome.storage.local`: допустим только `activeSessionId`. В Local/Session Storage и IndexedDB не должно быть prompt/response.
10. Проверьте клавиатурой focus-рамки, закрытие диалогов Escape, отсутствие горизонтального overflow в Side Panel и Workspace на узкой ширине.

## 4. Что прислать Codex

- PASS/FAIL для каждого пункта разделов 2 и 3.
- Путь созданной резервной копии.
- Фактический extension ID.
- Результат `check_native_host.ps1`.
- Для тестовой сессии: финальная phase/revision, четыре status, версия отредактированного ответа.
- Текст любых ошибок без пользовательских/секретных данных.
- Пути к скриншотам, только если вы их действительно сохранили; скриншоты не требуется добавлять в Git.

После проверки оставьте Native Host зарегистрированным. Не начинайте P1.0.5.
