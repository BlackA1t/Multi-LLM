# Multi-LLM — P0.4.1 результаты

Дата: 14 ноября 2026 года. Статус: `OFFLINE_TESTED`. Live Testing не выполнялся.

## Исправлено

### OAuth token lifecycle

- Перед каждым OpenAI `/models` и `/responses` запросом проверяется `expires_at` с защитным интервалом.
- Истёкший access token обновляется через официальный `grant_type=refresh_token` flow.
- Полный ротированный token set заменяется одной операцией в Windows Credential Manager.
- Async-lock и Windows file-lock сериализуют refresh внутри процесса и между процессами; после получения блокировки credentials перечитываются.
- Терминальные `invalid_grant`, `invalid_refresh_token`, `token_expired`, `refresh_token_expired`, `refresh_token_invalidated` и `refresh_token_reused` удаляют непригодный token set, сохраняют issued client registration и требуют явного `auth-chatgpt`.
- Временные HTTP/transport ошибки не удаляют refresh token и не запускают браузерный вход.

### Персистентные квоты

- `data/quota.db` хранит использованные и зарезервированные запросы/токены, числовые лимиты, reset, `Retry-After`, время последнего вызова и известные rate-limit headers.
- Резервирование выполняется атомарно через SQLite `BEGIN IMMEDIATE` до HTTP-вызова.
- Состояние восстанавливается независимым экземпляром CLI; неизвестный числовой лимит блокирует маршрут.
- При ошибке после отправки консервативно списывается резерв, поскольку невозможно доказать, что провайдер не учёл запрос.

### ZeroPaidPolicy и модели

- Раздельно требуются датированные источники для бесплатного тарифа, конкретного маршрута, аккаунта, внешней защиты от списаний, фактической модели и квоты.
- Локальный счётчик не считается доказательством отсутствия списаний.
- Семейство и разработчик берутся только из проверенной записи маршрута, а не из model ID.
- Запрошенная и фактическая модель сохраняются отдельно. Отсутствующий или неожиданный actual model ID является ошибкой; алиасы и подмена не разрешаются.
- Три участника обязаны иметь три разных проверенных family ID.

### Результаты и ресурсы

- Пустой текст, незавершённый/повреждённый SSE, SSE error, несколько terminal events, неправильный usage и отсутствующие обязательные поля не считаются успехом.
- HTTP-клиенты закрываются после каталога моделей и после запуска.
- Структурные token/key/authorization поля редактируются перед SQLite и JSON-экспортом.
- Существующая SQLite-схема мигрирует колонку `actual_model_id` без удаления истории.

## Оставшиеся ограничения

- Доказательства состояния кабинета вводятся пользователем с источником и временем; приложение не может офлайн подтвердить внешний billing UI.
- Провайдеры используют несколько окон квот. Прототип хранит исходные headers, но до live-проверки применяет консервативные настроенные числовые пределы.
- Резерв, оставшийся после аварийного завершения, намеренно не освобождается автоматически до подтверждённого reset. Это безопасный отказ, но может потребовать ручной диагностики.
- Строгое сравнение model ID может потребовать выбрать канонический ID, который провайдер возвращает в ответе; неизвестный alias не принимается автоматически.
- OAuth, доступные модели, реальные quota headers, региональные ограничения и внешняя защита от списаний не проверялись на пользовательских аккаунтах.

## Готовность

Код готов к отдельной проверке аккаунтов и каталогов моделей. Перед первым inference необходимо подтвердить все шесть категорий доказательств и числовые лимиты. Никакие реальные API-вызовы или автоматический переход к Live Testing в P0.4.1 не выполнялись.
